# Architecture decisions and review gates

`DECISIONS.md` contains the initial ADRs; their statuses remain unchanged by foundation scaffolding. An implementation decision must state its scope, evidence, alternatives, security consequences and the affected contracts/gates. Passing compilation alone cannot accept an architectural feasibility claim.

## Workflow

1. Read the current ADR, `MASTER_AGENT_PLAN.md`, threat model and affected module specification.
2. Add `docs/ADR-NNN-short-name.md` with status **proposed**, context, decision, alternatives, migration/rollback, security/privacy/operational consequences, test evidence and named reviewer/owner fields. Never insert an invented owner or signature.
3. Preserve the previous record when superseding it. Link the new ADR and identify the exact changed assumptions and dependent modules.
4. Run implementation and integration/security negative tests for the affected contracts. Capture reproducible local evidence and limitations.
5. Request review through the repository's documented PR process. The responsible human accepts material architectural reversals and release/security decisions. Record the actual approval link/date only when it exists.
6. Update the implementation status and gate review after the evidence is reviewed. A pending prerequisite keeps dependent modules closed.

Proposed → accepted requires evidence and the applicable reviewer decision. Rejected and superseded records remain auditable. Do not silently replace Pingora, invent a custom HTTP/TLS parser, weaken TLS verification, or turn private origins into an undocumented allowlist exception.

## Mandatory stop and human review points

The implementation sequence and dependency graph in `MASTER_AGENT_PLAN.md` are authoritative. Module 00 must pass before 01/02; production runtime work waits for the Pingora Go/No-Go and config-distribution prerequisites. Every module needs code, unit/integration/security negative evidence and security review.

Human decisions are required for a Pingora No-Go architecture change, a material ADR reversal, security/release signoff and production activation. Live DNS, paid cloud, real billing and production operations require explicit authorization. Existing user authorization controls the operation's scope; do not invent repeated approval requirements for ordinary reversible implementation work.

The entire quality/release matrix, third-party or equivalent scoped professional security assessment, privacy/commercial review, on-call ownership, recovery drills and measured SLO/capacity evidence remain required. A workflow file, a scaffold, a green unit test or an unsigned checklist cannot replace those gates.
